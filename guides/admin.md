## 1. Overview

```
Browser ─► Cloudflare Access (gate 2) ─► Tunnel ─► Caddy ─► that employee's Hermes (gate 1: username/password)
Hermes  ─► egress (Squid, rules from Config/ohermes.conf) ─► internet      (employee networks have no direct route)
```

| Path | What it is | Who changes it |
|---|---|---|
| `.env` | System settings: stage, domain, Cloudflare, image versions, **central AI model + key** (`AI_*`), logs/backups | admin |
| `Config/ohermes.conf` | Website allow/deny rules (organization / department / person). Never visible to agents. Applied with `ohermes reconf` | admin |
| `Config/defaults.yaml` · `enforced.yaml` · `SOUL.md` | Hermes defaults, enforced settings, the agent persona — each file mounted read-only on its own | admin |
| `Users/<name>/` | One employee: `.env` (email, subdomain, department, password hash) · `compose.yml` · `config.yaml` · `data/` (memory, chats) · `model/` (personal AI model, mode 600) · `runtime/` (locked settings, regenerated at every start — do not edit) | `ohermes` / admin |
| `docker-compose.override.yml` | The employee list for Docker Compose — generated by `ohermes`, git-ignored | `ohermes` |
| `Infrastructure/caddy/generated/routes.caddy` | One exact web route per active employee — generated by `ohermes`, git-ignored | `ohermes` |
| `Organization-Knowledge/` | Read-only company knowledge for the agents, three levels (section 4) | HR / Security / Marketing / department heads |
| `Archive/` | Employees who left (all data kept, nothing deleted) | `ohermes` |
| `Logs/` · `Backups/` | Logs and backups | `ops` container |
| `Infrastructure/` | Caddy, egress proxy, `hermes/setup.py` (settings lock), org-guard plugin, ops, deploy, host firewall helper | maintainers |

## 2. Install

### 2.1 Development (your own machine)

```bash
cp .env.example .env          # dev defaults; set AI_PROVIDER, AI_MODEL, AI_API_KEY
docker compose up -d
./ohermes create -e john.doe@example.com -s john -d IT -t Developer   # asks for a password; applies web rules
# open http://john.localhost:8080
```

- The first `docker compose up -d` before any web rules exist starts `egress` in **deny-everything** mode
  (fail closed) until `./ohermes reconf` or the first `create` runs.
- `STAGE=dev` turns off the Cloudflare checks — **never use it on a server reachable from the internet**.

### 2.2 Production (Linux server)

1. Install Docker Engine 28+ with the Compose plugin v2.33.1+.
2. Clone your organization's **private** copy of this template as root (the checkout must belong to root, see
   [deploy.md](deploy.md)), then `cp .env.example .env` and set:

   ```
   STAGE=prod
   COMPOSE_PROFILES=tunnel
   HERMES_DOMAIN=hermes.example.com
   PUBLIC_SCHEME=https
   PUBLIC_PORT_SUFFIX=
   CLOUDFLARE_TUNNEL_TOKEN=<from Cloudflare>
   ORIGIN_SECRET=<openssl rand -hex 32>
   BACKUP_AGE_RECIPIENT=<age1… — keep the private key off the server>
   AI_PROVIDER=<provider id>         # e.g. anthropic, openai-api, gemini, openrouter (section 7)
   AI_MODEL=<model id>               # e.g. claude-sonnet-5-5 for anthropic
   AI_API_KEY=<organization key straight from that provider — set a spending limit there>
   ```

   Every image is pinned to a version and digest in `.env.example`; change versions only after testing on dev.
   `chmod 600 .env`.
3. Cloudflare (section 2.3).
4. `sudo docker compose up -d` → `sudo ./ohermes reconf` → add employees with `sudo ./ohermes create …`.
5. Run once: `sudo chmod 700 Backups Archive`.
6. Optional but recommended: the host firewall helper (section 11).

#### `.env` keys

| Key | Meaning |
|---|---|
| `STAGE` | `prod` (Cloudflare checks on) or `dev` (local only) |
| `COMPOSE_PROFILES` | `tunnel` starts `cloudflared` |
| `HERMES_DOMAIN` | Employees get `https://<subdomain>.<HERMES_DOMAIN>` |
| `PUBLIC_SCHEME` · `PUBLIC_PORT_SUFFIX` | `https` and empty in prod; `http` and `:8080` in dev |
| `CADDY_BIND` · `CADDY_PORT` | Where Caddy is published on the host (default `127.0.0.1:8080`) |
| `CLOUDFLARE_TUNNEL_TOKEN` | Token of the Cloudflare tunnel |
| `ORIGIN_SECRET` | ≥ 32 characters (hex/alphanumeric); Cloudflare adds it as `X-Hermes-Origin`. Missing/short = every request 403 |
| `*_IMAGE` | Pinned images (`tag@sha256:…`) |
| `AI_PROVIDER` · `AI_MODEL` · `AI_BASE_URL` · `AI_API_KEY` | Central AI model (section 7) |
| `AI_PROVIDER_HOSTS` | Extra provider host names the proxy always allows (empty = derived from provider/base URL) |
| `DEFAULT_CPUS` · `DEFAULT_MEMORY` | Limits for new employees (`EMP_CPUS`/`EMP_MEMORY` per person) |
| `NETWORK_PREFIX` | First two octets of the employee networks (default `10.213` → one /28 per employee) |
| `LOG_RETENTION_DAYS` · `LOG_ARCHIVE_ACTION` · `LOG_ARCHIVE_KEEP_DAYS` | Log rotation (section 10) |
| `BACKUP_KEEP_DAILY` · `BACKUP_KEEP_WEEKLY` · `BACKUP_AGE_RECIPIENT` | Backups (section 10) |
| `TZ` | Time zone for logs and jobs |

### 2.3 Cloudflare (Tunnel, Transform Rule, Access)

1. **Tunnel** → public hostname `*.hermes.example.com` → service `http://caddy:80`.
2. **Transform Rule** (Rules → Transform Rules → Modify Request Header) for `*.hermes.example.com`:
   set `X-Hermes-Origin` = the value of `ORIGIN_SECRET`. Without it Caddy answers 403 to everything.
3. **Access — catch-all application (required)**: one Access application for `*.hermes.example.com` that allows
   only your identity-provider group (or nobody). Caddy checks that an Access token is *present* but cannot
   verify its signature or audience (stock Caddy has no JWT validation), so every hostname under the domain
   must be behind Access. The catch-all also keeps a new subdomain closed until its own application exists.
4. **Access — one application per employee**: `<subdomain>.hermes.example.com`, allow only that employee's
   email (the `-e` of `ohermes create`). More specific applications win over the catch-all.
5. Optional, stronger: in the tunnel's public-hostname settings enable **Protect with Access** (cloudflared
   validates the Access token with your team name and the application audience before Caddy sees the request).

Caddy itself only serves the exact employee hosts listed in `Infrastructure/caddy/generated/routes.caddy`
(rebuilt by `ohermes`); any other host name — container or service names, a changed subdomain — gets 404.

## 3. `ohermes` command reference

Run on the server with `sudo` (Linux). `<user>` = server name (`jane-smith`) or email.

| Task | Command |
|---|---|
| New employee | `sudo ./ohermes create -e jane.smith@example.com -s jane -d Sales -t "Sales Manager"` → asks for the password twice (shown as `*`, min. 12 characters) → add the Cloudflare Access application |
| Move department / new title | `sudo ./ohermes update -u jane-smith -d IT -t "Engineer"` → moves the personal folder, restarts only them |
| New email / subdomain | `sudo ./ohermes update -u jane-smith -e new@example.com -s jane2` → update Cloudflare Access; the old link stops working at once (Caddy routes are rebuilt and reloaded) |
| Employee leaves | **remove Cloudflare access + revoke personal API keys first** → `sudo ./ohermes rm -u jane-smith` → `Y` (stops the container, moves everything to `Archive/<name>_<date>/`) |
| Employee returns | `sudo ./ohermes restore -u jane-smith` → give Cloudflare access again |
| Reset password | `sudo ./ohermes repasswd -u jane-smith` (signs out all sessions) |
| List | `./ohermes ls` (name · email · subdomain · department · title · status · `ORG` = Organization-Knowledge folders `ok`/`missing` · model (central/personal) · link) |
| Personal AI model | `sudo ./ohermes model -u jane-smith` · `--show` (key: last 4 characters) · `--reset` (back to central) |
| Rebuild generated files | `sudo ./ohermes sync` (override file, Caddy routes, runtime files; restarts nothing) |
| Check web rules + `[organization-knowledge]` | `./ohermes check` |
| Apply web rules | `sudo ./ohermes reconf` · preview: `./ohermes reconf --dry-run` |
| Help | `./ohermes --help` · `./ohermes create --help` |

- **Server name** comes from the email at `create`: local part, lowercase, every character other than a-z 0-9 →
  `-` (`Jane.Smith@example.com` → `jane-smith`). It names the folders, container, network and login, and never
  changes (not even with a new email). Names must be unique including `Archive/` (case-insensitive); reserved:
  `assign caddy cloudflared ops egress edge outbound`.
- **Subdomain**: a-z 0-9 `-`, 1–63 characters, not starting/ending with `-`. Email and subdomain must be unused
  (including `Archive/`).
- **Department**: `-d sales` matches an existing department case-insensitively; a new one is capitalized
  (`Sales`); none → `General`.
- Prefer leaving out `-p`: a password on the command line stays in the shell history.
- `rm` moves the personal Organization-Knowledge folder into the archive too; `restore` puts it back
  (unless `manage_folders = off`, section 4).

### Doing it by hand (without `ohermes`)

1. Copy `Users/_template` → `Users/<name>` and replace `__USER__` with `<name>` in `compose.yml`.
2. Create `Users/<name>/.env` with the `EMP_*` variables (see an existing employee): `EMP_USERNAME`, `EMP_EMAIL`,
   `EMP_SUBDOMAIN`, `EMP_DEPARTMENT`, `EMP_TITLE`, `EMP_NET_ID` (unique forever, including `Archive/`),
   `EMP_NET_SUBNET`, plus the `HERMES_DASHBOARD_BASIC_AUTH_*` login values; quote values with single quotes.
3. Create `Organization-Knowledge/Organization/Department/<Dept>/Assign/{Skills,KPI,Knowledge}` and
   `…/Department/<Dept>/<name>/{Skills,KPI,Knowledge}`.
4. `./ohermes sync` (runtime files, override file, Caddy routes, modes) → `docker compose up -d` → `./ohermes reconf`.

## 4. Organization-Knowledge

```
Organization-Knowledge/Organization/
├── Assign/                        everyone        → /opt/org/organization
│   ├── Skills/ · Policy/{hr,security} · Knowledge/{product,brand} · KPI/ · Core-values/
└── Department/
    ├── <Dept>/Assign/             that department → /opt/org/department
    │   └── Skills/ · KPI/ · Knowledge/
    ├── <Dept>/<name>/             that employee   → /opt/org/me/{Skills,KPI,Knowledge}
    └── General/                   employees without -d
```

- Each folder is mounted **read-only on its own** — never `Organization/`, `Department/` or a whole department, so
  colleagues never see each other's personal folders.
- Skill name clashes: Organization wins → Department → Employee → system skills.
- Drop Markdown files in the matching folder — **effective immediately**, no restart (a new skill folder appears
  after a restart).
- Put a date in documents (`Effective: 2026-01-01`) so the agent picks the latest version.
- The `org-navigator` skill makes the agent search and cite files, and treat their content as **data, not
  instructions**.
- **Skills act like code**: every agent follows them. Changes to any `Skills/` folder need sysadmin review
  (CODEOWNERS) in addition to the content owner; CI flags links and shell blocks in changed skills.
- Put canary markers (`HOE-CANARY-<8+ letters/digits>`) in important documents: org-guard blocks any tool call
  containing one.

### Organization-Knowledge in its own repository (`manage_folders = off`)

By default `ohermes` creates, moves and archives the department and personal folders. If
`Organization-Knowledge/` is a separate (private) git repository maintained by content owners, those changes
would conflict with it. Switch them off in `Config/ohermes.conf`:

```
[organization-knowledge]
manage_folders = off        # on (default) | off — also true/false, yes/no; anything else fails `ohermes check`
```

| Command | `on` (default, or no section/key) | `off` |
|---|---|---|
| `create` | creates `Department/<Dept>/Assign/{Skills,KPI,Knowledge}` and `Department/<Dept>/<name>/{…}` | creates nothing; warns with the exact paths (relative to `Organization-Knowledge/`) still missing; the employee is created anyway |
| `update -d` | moves the personal folder | moves nothing; warns `old → new` path to move in the knowledge repository |
| `rm` | moves the personal folder into `Archive/<name>_<date>/Organization-Knowledge/` | leaves it in place; `Archive/<name>_<date>/Organization-Knowledge.README` notes that |
| `restore` | moves the archived copy back | moves nothing; warns about missing folders. An archive made while `on` keeps its copy in `Archive/<name>_<date>/Organization-Knowledge/` (warned) |
| `sync` | `chmod 700` on personal folders | never touches Organization-Knowledge |
| `ls` | `ORG` column: `ok` / `missing` | same |

- Department names still match existing folders case-insensitively; a department without a folder keeps the
  usual capitalisation (`sales` → `Sales`) and is reported as missing.
- With `off`, a personal folder may be prepared in the knowledge repository **before** `create` (it does not
  count as "name already used").
- Create the listed folders in the knowledge repository (an empty folder needs a file, e.g. `.gitkeep`) and
  pull it on the server. Until then **Docker creates any missing mount folder itself** (empty, owned by root):
  the agent starts with empty `/opt/org/...` folders. This is expected; the pull later fills them (a root-owned
  empty folder may need `sudo` for that pull).
- Switching between `on` and `off` is safe at any time; `rm` with one setting and `restore` with the other works.

## 5. Website rules — `Config/ohermes.conf`

Employee networks are `internal` (no direct route, outside names do not resolve). The only way out is the
`egress` container (Squid), used through `HTTP(S)_PROXY=http://egress:3128`. HTTPS is not decrypted — rules match
the host name only.

**Format**

- Sections: `[web]` (`default allow|deny`) · `[web:organization]` · `[web:department=<Dept>]` ·
  `[web:user=<server name>]` — the same file also holds `[organization-knowledge] manage_folders = on|off`
  (not a web rule, see section 4); `ohermes check` validates both.
- One rule per line: `<allow|deny>  <site>  <comment>` — site = `example.com` (that host only),
  `*.example.com` (the domain and every subdomain) or **one IP** (`203.0.113.10`, `2001:db8::1`). No paths/ports.

```
[web]
default   deny
[web:organization]
allow     registry.npmjs.org  browser driver (first start of each employee)
allow     models.dev          model catalog, fetched at every start
deny      *.facebook.com      not work related
[web:department=Sales]
allow     *.salesforce.com    CRM
[web:user=jane-smith]
allow     canva.com           slides
```

**Decision order** (first match wins)

1. Always refused: ports other than 443 (CONNECT) / 80, more than 200 open connections from one agent,
   destinations resolving to private/special ranges (10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16,
   127/8, 0/8, multicast, reserved, documentation, IPv6 private/NAT64). The name is decided **before** DNS:
   under `default deny` a name that is not allowed is never resolved (no DNS side channel).
2. The AI provider hosts (central, and each personal model for its owner) are **always allowed**.
3. Any deny (organization → department → person) — **deny always wins**.
4. Any allow.
5. Raw-IP destinations are refused in both modes unless that IP has its own `allow` line; names never match
   through reverse DNS.
6. `default allow` → allowed · `default deny` → refused (no file / no default line = allow).

- People are identified by their /28 subnet (`EMP_NET_SUBNET`); departments by their active members' subnets.
  `update -d` moves the rules with the person.
- **Apply**: edit the file → `sudo ./ohermes reconf` (check → generate `rules.conf.new` → `squid -k parse` → swap
  → `squid -k reconfigure`; any failure keeps the previous rules and exits ≠ 0). No agent restarts.
  `create`/`update`/`rm`/`restore` run it for you.
- **Log**: `Logs/egress/access.log` (time · `client=` subnet · destination · status · `result=TCP_DENIED` when
  blocked). Plain-HTTP entries keep the full URL including the query string; HTTPS shows `host:443` only.
  The log is root-only on the host. Who is an IP: `grep EMP_NET_SUBNET Users/*/.env`.
- `default allow` only blocks what you list — prefer `default deny` once you know which sites people need.
  The template ships `default allow` so a fresh install works; switch to `default deny` for production.
  `default deny` needs `allow registry.npmjs.org` for the browser driver (section 9) and `allow models.dev` for
  the model catalog (section 6; without it the previous copy is used, or none on a first start).

## 6. Locked Hermes settings

At every container start `Infrastructure/hermes/setup.py` (root) regenerates `Users/<name>/runtime/`, then Hermes
starts. Everything below is mounted **read-only** into `/opt/data` (the agent's home):

| `runtime/` file | Mounted at | Content |
|---|---|---|
| `config.yaml` | `/opt/data/config.yaml` | `Config/defaults.yaml` → `Users/<name>/config.yaml` → AI model → `Config/enforced.yaml` → generated values (later wins) |
| `hermes.env` | `/opt/data/.env` | `API_SERVER_KEY`, the AI key, `HERMES_REDACT_SECRETS=true` |
| `auth.json` | `/opt/data/auth.json` | empty credential store |
| `SOUL.md` | `/opt/data/SOUL.md` | the persona from `Config/SOUL.md` |
| `active_profile` | `/opt/data/active_profile` | always empty (default profile) |
| `shell-rc` | `/opt/data/.profile` `.bash_profile` `.bash_login` `.bashrc` `.bash_logout` `.inputrc` | always empty — no code can be planted in shell start files |
| `hooks/` · `empty/` | `/opt/data/hooks` · `/opt/data/profiles` | empty — no gateway hooks, no Hermes profiles |
| `skills/` · `org-skill-names.json` | `skills.external_dirs` | company skills after removing duplicate names |
| `provider-facts.json` | (setup.py only) | Hermes' provider tables from the image — last good copy for the provider lock |
| `models_dev_cache.json` · `.etag` | `/opt/data/models_dev_cache.json` · `.etag` | the models.dev catalog (provider definitions, model lists) fetched from `https://models.dev/api.json` at start; Hermes cannot refresh it (`models_dev.url` points at a closed port), so it changes only at the next start |

The whole `plugins/` folder (org-guard) is mounted read-only as well. Key enforced settings
(`Config/enforced.yaml`):

| Setting | Effect |
|---|---|
| `agent.disabled_toolsets: [web, search, delegation, code_execution, cronjob, connections, browser-cdp, browser-use]` | no outside search/extract services, sub-agents, `execute_code`, cron, MCP installs, raw CDP |
| `browser.cloud_provider: local` · `browser.backend: "off"` | local Chromium through the egress proxy |
| `memory.write_approval` · `skills.write_approval: true` | the employee approves memory/skill changes (`/memory pending`, `/skills pending`) |
| `terminal.auto_source_bashrc: false` · `shell_init_files: []` | Hermes never sources shell start files from the agent's home |
| `security.redact_secrets` · `allow_private_urls: false` · `allow_lazy_installs: false` | redaction, no internal URLs, no on-demand package installs |
| `approvals.deny` | shell commands always refused: reading the environment or secret files (`.env`, `auth.json`, `/opt/enterprise/runtime`, `/opt/enterprise/model`), starting another Hermes |
| `plugins.enabled: [org-guard]` · `org_guard.min_org_chars: 200` | the guard plugin and its copy threshold |
| `providers.<other>.enabled: false` (generated) | `/model` in a chat cannot switch to another provider or a local endpoint |

Other hardening in `Users/_template/compose.yml`: read-only root filesystem with size-capped tmpfs,
`cap_drop: ALL` + five capabilities for the start-up step, `pids: 512`, `PYTHONNOUSERSITE=1` (no `.pth` code from
the agent's home), and a `PATH` without the agent-writable `~/.local/bin` in front.

- Settings pages in the dashboard, `hermes config set` and `hermes plugins …` fail (by design). Tell employees:
  *"The settings pages of your Hermes are read-only. `/model` can only choose models of the provider the
  organization set, for that conversation. Ask the administrators for changes."*
- After editing `Config/*.yaml` or `Users/<name>/config.yaml`: `docker compose up -d --force-recreate` (everyone)
  or `docker compose restart <name>`.
- If `setup.py` fails on a first boot, Hermes does **not** start (fail closed); on later boots it keeps the
  previous locked settings and logs `ERROR`.
- **Host file modes (Linux)**: `Users/` and `Users/<name>/` 0700 root · `runtime/` 0750 `root:10000` ·
  `runtime/hermes.env`/`config.yaml`/`auth.json` 0640 · `model/` 0700 with 0600 files · personal
  Organization-Knowledge folders and `Archive/` 0700. `ohermes` and `setup.py` set these at every run.

## 7. AI model and key

- **Central** (everyone): `.env` → `AI_PROVIDER` (Hermes provider id: `openrouter`, `anthropic`, `openai-api`,
  `gemini`, `deepseek`, … or `custom` with `AI_BASE_URL`), `AI_MODEL`, `AI_API_KEY` → `docker compose up -d`.
- **Personal**: `sudo ./ohermes model -u <name>` on the server runs Hermes' own model picker in a throwaway
  container, keeps only the model + key in `Users/<name>/model/` (mode 600), restarts that employee and allows
  that provider's host for them only. Personal wins over central; `--reset` returns to central.
- Only API-key providers are supported (no OAuth logins).
- The key reaches Hermes only through the read-only `/opt/data/.env`; the `AI_*` variables are removed from the
  environment first. The agent **can still read the key** (Hermes needs it) — set a spending limit; org-guard
  redacts it from tool output and blocks tool calls that contain it.
- The provider lock disables every other provider id from Hermes' own tables (read from the image; a saved copy
  is used if that step fails; with neither, setup stops — fail closed) and from the models.dev catalog, which is
  read-only and fixed at start (no provider can be added afterwards).

## 8. org-guard

The organization's Hermes plugin (`Infrastructure/hermes/plugins/org-guard`, mounted read-only).

**Before a tool runs** (`pre_tool_call` — if the plugin fails, the call is blocked):

- (a) secret values present in the container (AI key, dashboard secret/hash, any `*KEY/TOKEN/SECRET/PASSWORD`
  variable ≥ 8 characters) raw, base64, hex, url-encoded or in fragments — every tool
- (b) common key formats (`sk-…`, JWT, PEM private keys, AWS, GitHub, Slack, Google, Stripe) — every tool
- (c) Thai personal data (national ID with checksum, phone numbers) and emails other than the owner's —
  **outbound tools**
- (d) canary markers `HOE-CANARY-…` — every tool
- (e) ≥ `org_guard.min_org_chars` (200) characters copied verbatim from Organization-Knowledge — **outbound tools**
- (f) starting another Hermes / agent from the shell
- (g) changes to what shapes future sessions: `memories/`, `skills/`, `SOUL.md`, files named like memory/skill/
  instruction files (`MEMORY.md`, `USER.md`, `SKILL.md`, `AGENTS.md`, `CLAUDE.md`, `.hermes.md`, `.cursorrules`,
  …), `plugins/` `hooks/` `profiles/` `config.yaml` `.env`, and **shell/tool start files** in the home folder
  (`.bashrc`, `.profile`, `.gitconfig`, `.npmrc`, `.ssh/`, `.config/git`, Python user site, `sitecustomize.py`,
  `*.pth`; also `git config --global`, `npm config set`, `pip install --user`). File tools ask the employee
  (read-only locations are blocked); shell commands may only read these paths.
- (h) creating FIFOs / device files
- (i) reading files that hold a copy of a secret (`/opt/data/.env`, `/opt/enterprise/runtime/hermes.env`,
  `/opt/enterprise/model/`, the s6 environment, `/proc/*/environ`)
- Uploads (`curl -F/-T`, `scp`, `rsync host:`, `git push`) and form submits after typing need the employee's
  approval.

**Outbound** = every tool except the local ones (files, memory, skills, todo, session search, kanban board) — so
`vision_analyze`, `text_to_speech`, image/video tools, MCP and messaging tools are checked by (c) and (e) too —
plus shell commands that can reach the network.

**After a tool runs**: invisible Unicode is stripped, secret values are redacted (`[REDACTED by org-guard]`), and
content from websites, URL-fetching tools and files outside Organization-Knowledge is wrapped as untrusted data.

**Log**: one line per block/approval in `docker compose logs <name>`:
`ORG-GUARD BLOCK user=… tool=… reason=… src=… seq=… sig=…` (never a secret value). Lines are signed with a
per-process key announced once (`ORG-GUARD KEY …`) in the container log, which the agent cannot read. Verify:

```bash
docker compose logs --no-log-prefix <name> | python3 Infrastructure/hermes/verify_guard_log.py
```

Unsigned, badly signed or re-numbered lines are reported as forged. The agent can still delete its own files
under `/opt/data/logs`; the egress log on the host is the authoritative record of outbound traffic.

**Limits**: it is a pattern filter, not a sandbox — split, re-worded or obfuscated leaks can pass. The hard limits
are the egress proxy and the read-only mounts.

Tests: `docker run --rm --network none -v "$PWD/Infrastructure/hermes/plugins/org-guard:/g:ro" --entrypoint
/opt/hermes/.venv/bin/python <HERMES_IMAGE> -m unittest discover -s /g/tests -v` · live regression checks of a
running employee: `sudo Infrastructure/hermes/tests/live-check.sh <name>`.

## 9. Browser

- Chromium is in the image; the `agent-browser` driver is installed in the background at each employee's first
  start (`hermes pm install agent-browser`, pinned version and sha256 from the image's lock file) into
  `/opt/data/tools`, through the egress proxy. Log: `browser driver (agent-browser) installed`.
- Under `default deny` add `allow registry.npmjs.org` to `[web:organization]`, or the install fails
  (`WARNING: could not install the browser driver`) → add it, `ohermes reconf`, `docker compose restart <name>`.
- The browser goes through the egress proxy, so the website rules apply to it.

## 10. Logs and backups

The `ops` container (no network) runs:

| Time | Job |
|---|---|
| 00:15 | Collect yesterday's Docker logs → `Logs/docker/<service>/<date>.log.gz`; Caddy/egress/Docker logs older than `LOG_RETENTION_DAYS` (30) → `Logs/archive/`; archive older than `LOG_ARCHIVE_KEEP_DAYS` (365) deleted |
| 02:00 | Back up every employee in `Users/` + the whole `Organization-Knowledge/` → `Backups/daily` (Sundays → `weekly`); archived employees once → `Backups/archive`; encrypted with age when `BACKUP_AGE_RECIPIENT` is set |

- Run now: `docker compose exec ops /ops/backup.sh` · `docker compose exec ops /ops/logs.sh`
- **Copy `Backups/` off the server** (e.g. rclone from the host).
- Backups contain `.env` files, AI keys and all conversations: `sudo chmod 700 Backups` and set
  `BACKUP_AGE_RECIPIENT`.
- Restore one employee: stop them → extract over `Users/<name>/` → `docker compose up -d`:
  `age -d -i key.txt Backups/daily/<name>-<time>.tar.gz.age | tar -xz -C Users/`

## 11. Host hardening

- **Patch** the kernel, Docker Engine and OS at least monthly (and at once for container-escape issues);
  re-pin new image digests after testing on dev.
- **Host firewall (optional, recommended)**: employee networks still have a host address (their gateway). Any
  host service listening on `0.0.0.0` (sshd, monitoring, databases) is reachable from agents through it.
  `Infrastructure/host/firewall.sh` adds two iptables rules (new connections from `NETWORK_PREFIX.0.0/16` to the
  host, and from that range to anything outside it, are dropped):

  ```bash
  sudo Infrastructure/host/firewall.sh apply     # status | remove
  # test from an employee container: no connection to its gateway, e.g. port 22
  docker exec <container> sh -c 'timeout 5 bash -c "</dev/tcp/<gateway-ip>/22" && echo OPEN || echo closed'
  ```

  Persist the rules with your distribution's tools.
- **Disk**: `/opt/data` of each employee is a host folder without its own quota. Put `Users/` on its own
  filesystem (or an XFS project quota) and monitor free space; tmpfs sizes and process counts are already capped.
- Only trusted people get root on the server: root can read every conversation (inform employees — privacy law).

## 12. Upgrades

- `git pull` (or the automatic deploy) → `sudo ./ohermes sync` → `sudo docker compose up -d` →
  `sudo ./ohermes reconf`. `sync` regenerates `Users/<name>/compose.yml` from the template when it is outdated
  (the old file is kept as `compose.yml.old`) and rebuilds the Caddy routes.
- **This release** (exact Caddy routes, shell start-file mounts, provider lock, pids limits): run
  `sudo ./ohermes sync` then `sudo docker compose up -d` — every employee's compose file is regenerated (new
  network alias `<name>.employee.internal`, read-only shell start files, `pids`, `PATH`), and add the
  catch-all Access application (section 2.3).
- Older releases: website rules moved to `Config/ohermes.conf` (`sync` moves an old `./ohermes.conf`); personal AI
  keys in `Users/<name>/.env` are no longer used (`ohermes model -u <name>`).

## 13. Troubleshooting and gotchas

| Symptom | Cause / fix |
|---|---|
| Every request 403 in prod | `ORIGIN_SECRET` missing/short, or the Cloudflare Transform Rule does not set `X-Hermes-Origin` |
| 404 for an employee | Host not in `Infrastructure/caddy/generated/routes.caddy` → `sudo ./ohermes sync` |
| Employee container does not start, names a missing file | `runtime/*` must exist before `up` → `sudo ./ohermes sync` |
| All websites refused after install | No web rules yet → `sudo ./ohermes reconf` |
| `models.dev catalog not reachable` in the log | allow `models.dev` in `Config/ohermes.conf`, `ohermes reconf`, restart the employee |
| `could not install the browser driver` | allow `registry.npmjs.org` (section 9) |
| `[stage2] Warning: chown /opt/data/profiles failed` at every start | normal (read-only by design) |
| Settings cannot be saved in the dashboard | by design (section 6) |
| A tool cannot reach the internet | it ignores proxy variables — fail closed by design (Node needs `NODE_USE_ENV_PROXY=1`, set) |

- Never set `COMPOSE_FILE` in `.env` (Compose would skip `docker-compose.override.yml`).
- Never change or reuse `EMP_NET_ID`; never edit `runtime/`, `docker-compose.override.yml` or
  `Infrastructure/caddy/generated/` by hand.
- Do not edit files in `Users/<name>/data/` while the container runs.
- Windows dev machines: `ohermes` converts paths with `cygpath`; use `MSYS_NO_PATHCONV=1` for
  `docker exec … /opt/...`. Docker Desktop warns about SQLite on bind mounts (dev only).
