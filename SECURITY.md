# Security

## Reporting a vulnerability

**Please do not open a public issue for security problems.**

- Report privately through GitHub Security Advisories only —
  `https://github.com/Kissofbeauty/hermes-open-enterprise/security/advisories/new` ("Report a vulnerability").

Include the affected version/commit, the component (`ohermes`, setup.py/locked config, org-guard, egress,
Caddy, ops, deploy), reproduction steps on a dev stage, and the impact. Remove real secrets and personal data.
We aim to acknowledge reports within 5 working days and to agree on a disclosure date with you; credit is given
unless you prefer otherwise.

Vulnerabilities in Hermes Agent itself belong to the Hermes Agent project (Nous Research); report them there.
Bypasses of the documented limitations below (e.g. a re-worded leak passing org-guard) are known — reports that
show a practical, generic bypass are still welcome.

## Supported versions

| Version | Supported |
|---|---|
| 0.6.x (latest) | Yes |
| < 0.6 | No (never publicly released) |

Only the latest minor release receives security fixes. Pinned image digests are updated in releases after
testing; you are responsible for patching your host kernel and Docker Engine.

## Design assumptions
- **Entry**: in production Caddy accepts a request only if it carries `X-Hermes-Origin: <ORIGIN_SECRET>`
  (added by a Cloudflare Transform Rule) **and** a `Cf-Access-Jwt-Assertion` header. Caddy does not verify the
  JWT signature or audience (stock Caddy has no JWT validation); the origin secret is what proves the request
  came through Cloudflare. **Cloudflare Access must therefore cover every hostname of the domain**: a catch-all
  Access application for `*.<domain>` (deny by default) in addition to the per-employee applications, or
  "Protect with Access" on the tunnel hostname. Caddy serves only the exact hosts in the generated
  `Infrastructure/caddy/generated/routes.caddy` (one per active employee, rebuilt by `ohermes` and reloaded
  gracefully) and proxies only to `<name>.employee.internal` network aliases; any other host — container or
  service names, an old subdomain — gets 404. Caddy is bound to 127.0.0.1 and reached through the tunnel. Caddy removes `X-Hermes-Origin`, `Cf-Access-Jwt-Assertion` and the
  `CF_Authorization` cookie before proxying (Hermes does not use them, and the agent runs in the Hermes
  container), and deletes them plus `Cookie`/`Authorization` headers from its logs.
- **Isolation**: each employee's Hermes is on its own `internal` Docker network; only Caddy and the egress proxy
  join them. Caddy refuses requests from employee networks and the proxy refuses private destinations. In
  production the cross-tenant barrier at Caddy is `ORIGIN_SECRET`; container isolation relies on the host kernel
  and Docker Engine — keep them patched.
- **Pre-login information**: Hermes serves version/host details on a few `/api` paths without a login; Caddy
  passes them only for a logged-in session (forward_auth to Hermes' `/api/auth/me`) and returns 404 for
  `/api/cron/fire`.
- **AI provider lock**: every provider except the admin-set one is disabled in the locked config, so `/model` in a
  chat cannot switch to another provider or a local endpoint, and it has no option for a custom base URL or key.
  The provider list comes from Hermes' own tables in the image, read by a child process that opens no
  agent-controlled file; a root-owned last good copy is used if that fails, and with neither the start-up step
  stops (Hermes keeps its previous locked settings, or does not start on a first boot). Hermes also builds
  provider definitions (base URL, key variable) from its models.dev catalog: `setup.py` fetches that catalog from
  `https://models.dev/api.json` at every start and mounts it **read-only** at `/opt/data/models_dev_cache.json`
  (empty read-only ETag too), every provider in it except the active one is disabled, and Hermes' own refresh
  (`models_dev.url`) points at a closed local port — so no provider or endpoint can appear after start. If the
  catalog cannot be fetched the previous root-owned copy is used.
- **Logins**: Hermes dashboard basic auth, per employee, scrypt hash. It has no MFA — Cloudflare Access is the
  second factor and must not be skipped. `STAGE=dev` disables the Cloudflare checks: never use it on a
  server reachable from the internet.
- **Locked settings**: Hermes' `config.yaml`, `.env`, `auth.json`, `SOUL.md` (from `Config/SOUL.md`) and
  `active_profile` are generated by `setup.py` (root) at every start and bind-mounted **read-only**; `hooks/`, the
  whole `plugins/` folder and an empty `profiles/` too (a Hermes profile carries its own, unlocked config.yaml, so
  profiles are disabled: dashboard, `hermes -p` and `hermes profile use` fail). The agent (uid 10000), the
  dashboard and `hermes config set` cannot change tools, plugins, approvals, persona or the AI model/base URL.
  `setup.py` never follows a symlink in the agent-writable `/opt/data` (fd-relative `O_NOFOLLOW` + `fchown`);
  everything that imports Hermes or reads agent-controlled files (local skills, model cache) runs in a child
  process as uid 10000 with non-blocking, size-capped reads and a time limit. The Hermes root filesystem is
  read-only and all containers run with `cap_drop: ALL` plus only the capabilities they need.
- **Self-modification**: company skills (Organization-Knowledge) are read-only mounts and always rank above
  personal ones. Personal memory and skills stay agent-writable (Hermes writes them), so org-guard asks the
  employee before any file-tool write to `memories/`, `skills/`, `SOUL.md` or a file named like a memory, skill or
  project instruction file (`MEMORY.md`, `USER.md`, `SKILL.md`, `AGENTS.md`, `CLAUDE.md`, `.hermes.md`,
  `.cursorrules`, …) or a hard-linked file — relative paths are resolved with Hermes' own resolver (the
  session's working directory). In the shell it blocks: writes that name those folders/files (also through
  wildcards), `cd`/`pushd` into `memories/`, `skills/`, `plugins/`, `hooks/`, `profiles/`, any non-read-only
  command while the session's working directory (which Hermes keeps between commands) is inside one of them,
  creating FIFOs/device files, and starting another Hermes (`hermes`, `HERMES_HOME`, `hermes_cli`, …);
  `approvals.deny` repeats the Hermes-launch rules.
  **Shell start files**: the agent's home is `/opt/data`. `.profile`, `.bash_profile`, `.bash_login`, `.bashrc`,
  `.bash_logout` and `.inputrc` are empty, root-owned, read-only mounts, and `terminal.auto_source_bashrc` is off,
  so no code can be planted that runs before every command. `PYTHONNOUSERSITE=1` stops `.pth`/`usercustomize`
  code in the user site, `PATH` no longer puts the agent-writable `~/.local/bin` before system folders, and
  org-guard blocks writes to `.gitconfig`, `.npmrc`, `.ssh/`, `.config/git`, the Python user site,
  `sitecustomize.py`/`*.pth` and commands such as `git config --global`, `npm config set`, `pip install --user`.
  Residual: the browser driver under `/opt/data/tools` is agent-writable code that Hermes runs. At every start `setup.py` renames a non-regular `SKILL.md`
  (or a non-regular entry in `memories/`) to `<name>.quarantined-<time>` so it cannot hang Hermes. The shell
  checks are text-based: an obfuscated command (base64, `eval` of computed names) can still write
  `memories/`/`skills/` or start a nested Hermes with its own `HERMES_HOME` — that process runs with the agent's
  own rights and does not change the employee's chat, which keeps the locked config.
- **Secrets**: `.env` files are git-ignored. The AI key reaches Hermes only through the read-only
  `/opt/data/.env`; the central `AI_*` variables are removed from the environment before Hermes starts.
  Hermes runs its dashboard, gateway and the agent's tools as the same uid, so the agent **can still read** the AI
  key and the dashboard login hash/secret (`/proc/<pid>/environ`); Hermes has no file-based secret option.
  Mitigations: `approvals.deny` and org-guard refuse commands/reads that name the environment or secret files
  (`/opt/data/.env`, `/opt/enterprise/runtime/hermes.env`, `/opt/enterprise/model/`, the s6 environment,
  `/proc/*/environ`), and org-guard redacts these values from tool output and blocks tool calls that contain them. Set spending limits on the AI key.
- **org-guard** (`Infrastructure/hermes/plugins/org-guard`): `pre_tool_call` fails closed and blocks secret values
  (raw/base64/hex/url-encoded), common key formats, canary markers, Thai personal data and verbatim
  Organization-Knowledge (≥ 200 characters) going to outbound tools; uploads and form submits need the employee's
  approval. **Outbound** means every tool except a list of local ones (files, memory, skills, todo, session
  search, kanban board) — `vision_analyze` and other URL/service tools included — plus shell commands that can
  reach the network. Result transforms strip invisible Unicode and wrap outside content as untrusted. It is a
  pattern filter, not a sandbox: split or re-worded leaks can pass.
- **Audit trail**: org-guard writes one line per block/approval to the container's stderr, which the agent cannot
  open (root-owned pipe) and does not inherit. Lines are signed with a per-process key that lives only in memory
  and is announced once in the container log (`Infrastructure/hermes/verify_guard_log.py` flags unsigned or
  re-numbered lines). Residuals: a program Hermes starts without redirecting stderr (e.g. the agent-writable
  browser driver) could add a fake key line, and the agent can delete its own logs and sessions under
  `/opt/data`. The egress log on the host (root-only) is the authoritative record of outbound traffic; ship
  container logs off the host if you need tamper-proof records.
- **Organization-Knowledge** is mounted read-only, one folder at a time: `Organization/Assign`, the employee's own
  `Department/<Dept>/Assign` and their own `Skills/KPI/Knowledge`. Never mount `Organization/`, `Department/` or a
  whole department — personal folders of colleagues would become readable. Documents reach the agent as data;
  the org-navigator skill tells it not to follow instructions found in them, which reduces but does not remove
  prompt-injection risk. Only trusted people should be able to change these folders.
- **Website rules** (`Config/ohermes.conf`, never mounted into an agent — Hermes gets only `Config/defaults.yaml`,
  `enforced.yaml` and `SOUL.md`) are enforced by the `egress` proxy (Squid): employee networks are
  `internal: true` (no direct route, and Docker's DNS does not resolve outside names there), so agents reach the
  internet only through `http://egress:3128`. The proxy matches host names only (HTTPS is not decrypted), refuses
  ports other than 443/80, private/internal destinations and raw-IP destinations (unless an IP is explicitly
  allowed), and always allows the AI provider. With `default allow` only listed websites are blocked — prefer
  `default deny`. Website/search tools that fetch through outside services are disabled.
  Allowed websites can still receive data an agent is tricked into sending.
  Names are decided before DNS: every allow rule ends with `!to_private`, so under `default deny` a name that is
  not allowed is never resolved (no DNS side channel). The egress log keeps full plain-HTTP URLs including the
  query string (HTTPS: host:port only) and is root-only on the host.
- **Resources**: each Hermes container has CPU, memory and `pids: 512` limits and size-capped tmpfs; caddy,
  egress, ops and cloudflared have `pids: 256`; the egress proxy allows at most 200 connections per agent.
  `/opt/data` is a host folder without its own quota — put `Users/` on its own filesystem or quota.
- **Host**: employee networks still have a host address (their gateway). Services on the host listening on
  `0.0.0.0` are reachable from agents unless you apply a host firewall — `Infrastructure/host/firewall.sh`
  (optional, iptables `INPUT` + `DOCKER-USER`).
- **Host files (Linux)**: the checkout belongs to the admin account, which is in the `docker` group and therefore
  root-equivalent (accepted: it is the account that runs `docker compose`). Employee secrets stay root-only so
  that account does not read them by accident: `Users/<name>/secrets.env` (dashboard login hash + signing key)
  0600 root, `model/` and `data/` 0700, `runtime/hermes.env`/`config.yaml`/`auth.json` 0640 `root:10000`
  (Hermes reads them through its group), `Backups/daily|weekly|archive` 0700 root. `Users/`, `Users/<name>/`,
  `Archive/`, `Backups/`, `Logs/` are `root:<admin group>` 0750 and `Users/<name>/{.env,compose.yml,config.yaml}`
  0640 — what Docker Compose reads as the admin (no secret in them). The dashboard login reaches Hermes through
  a read-only mount read by `start.sh` (root), so it is no longer in `docker inspect`. The root `.env` (central AI
  key, Cloudflare token, `ORIGIN_SECRET`) is 0600, owned by the admin account. `ohermes` re-runs itself with
  `sudo` for the commands that need root; only the arguments cross that boundary.
- **Admins**: anyone with root on the server can read every employee's conversations and memory. Anyone who can
  merge to `main` effectively has root on the server (the deploy runs the repo's `ohermes` and compose files as
  root) — protect `main` with CODEOWNERS, required `production` reviewers and signed commits. The server checkout
  must belong to root or to the root-equivalent admin account: `deploy.sh` (root) refuses symlinked or
  foreign-owned log/lock files, but whoever owns the checkout could change what root runs. Organization-Knowledge `Skills/` act like code (every agent follows
  them): they need sysadmin review in CODEOWNERS and CI flags every change.
- **Backups** contain `.env`/`secrets.env` files and AI keys (`model/`, `runtime/`) and are unencrypted by default
  (accepted): they are root-only files; preferably set `BACKUP_AGE_RECIPIENT` and keep the private key off the
  server.
- **Accepted for the pilot**: one organization-wide AI key readable by every agent (spend limit at the provider;
  `ohermes model -u` for heavy users), the AI provider host always allowed by the proxy, `default allow`.
- **Supply chain**: every image is pinned to a version and digest; update only after testing on the dev stage.
  CI runs a secret scanner (gitleaks, pinned by digest) and Dependabot proposes Action/image updates.

## Known limitations

- `default allow` (the shipped web-rule default) only blocks listed websites; allowed websites can receive data
  an agent is tricked into sending. Prefer `default deny`.
- Caddy cannot validate the Cloudflare Access token: a catch-all Access application is required.
- org-guard is a pattern filter; obfuscated shell commands can bypass its text checks.
- The agent can read the AI key and the dashboard login secrets (same uid as Hermes); the AI provider host is
  always allowed.
- Prompt injection from documents, websites or memory is reduced, not eliminated.
- Agent-side logs are not tamper-proof (see *Audit trail*).
- Not yet verified end-to-end behind a real Cloudflare tunnel or with a real AI provider; Linux host file
  permissions are only partly tested.
